# MINH TRÍ — UNIVERSAL LEARNING CONTINUITY LAW — 2026-10-04

**Status:** STABLE OWNER LAW / CROSS-ARCHITECTURE INVARIANT  
**Scope:** ALL current and future learning tracks in MINH TRÍ  
**Authority:** Owner directive dated 2026-10-04. This law remains in force until explicitly superseded by a new Owner decision through protected project governance.

## 1. Purpose

MINH TRÍ must not depend on chat memory for learning continuity. Every material learning track must be recoverable by a new zero-chat seat from canonical project records and must continue from the latest durable checkpoint unless the Owner explicitly redirects the work.

## 2. Mandatory pre-work bootstrap

Before material work, every chat/seat must fresh-read the current authority chain from live canonical GitHub:

1. `docs/PROJECT_STATE.json`;
2. the `current_law_index` routed by PROJECT_STATE;
3. this Universal Learning Continuity Law;
4. the `current_architecture` routed by PROJECT_STATE;
5. `docs/GITHUB_FIRST_ROLE_BOOTSTRAP_20261002.md`;
6. for learning work, the active learning checkpoint/plan for that track;
7. the task/domain sources needed for the work.

A pasted SHA, model memory, chat summary, or user restatement is not sufficient current-state proof when live canonical state is available.

## 3. Mandatory durable learning record

Every material learning checkpoint in any domain must durably record at least:

- learning track/topic;
- what was learned;
- what misunderstanding or earlier claim was corrected;
- source/evidence used;
- claim/evidence status;
- current checkpoint;
- next checkpoint;
- open questions, audits, and unresolved uncertainty;
- material errors/corrections;
- provenance/date;
- durable GitHub location;
- Local Brain mirror status when applicable.

## 4. Mandatory handoff contract

A learning session is not durable unless a new zero-chat seat can recover:

TRACK  
→ LEARNED / CORRECTED  
→ EVIDENCE / STATUS  
→ CURRENT CHECKPOINT  
→ NEXT CHECKPOINT  
→ OPEN AUDITS / UNKNOWNS  
→ DURABLE RECORD LOCATION.

## 5. No silent loss

A new or resumed seat must not silently:

- restart a learning track from the beginning;
- drop a prior correction;
- drop an open audit or unresolved question;
- replace the recorded next checkpoint with a different path without Owner direction.

The default action is to continue from `NEXT CHECKPOINT`.

## 6. Recorded does not mean verified

Durable recording proves continuity, not truth.

Recording a claim must never silently promote evidence status, including:

- `UNTESTED → VERIFIED`;
- `SYNTHESIS → TEXT_ATTESTED`;
- `LATER/PARACANONICAL → EARLY TEXT`;
- a single translation → the only possible lexical meaning.

Every learning record must preserve its evidence class and uncertainty.

## 7. Cross-domain scope

This law applies to every learning track, including but not limited to:

- Buddhist thought;
- economics;
- PC/workshop skills;
- YouTube;
- music;
- Suno;
- CapCut;
- directing/editorial work;
- software;
- business;
- languages;
- science;
- all future learning domains.

No domain-specific learning record can opt out of this continuity rule unless the Owner explicitly changes the law.

## 8. Blocked write-path rule

If durable recording is blocked:

1. do not bypass branch protection or security gates;
2. state exactly that the checkpoint is **NOT YET DURABLY RECORDED**;
3. preserve the blocker in a durable issue/record when a safe write channel exists;
4. continue independent work that does not require the blocked mutation;
5. complete the protected branch → PR → required CI → merge → fresh-read sequence when the write path becomes available.

Issue #171 is the originating durable Owner directive/blocker record for this law. The issue does not replace integration into authority files.

## 9. Architecture routing invariant

The following current authority surfaces must route this law and agree on the active learning checkpoint semantics:

- PROJECT_STATE;
- current Law Index;
- current Architecture;
- role bootstrap;
- Recovery Manifest;
- consistency tests;
- active learning checkpoint/registry records.

A routing mismatch is a project consistency defect and must fail closed.

## 10. Protected change rule

This law may be changed only through protected project governance:

branch  
→ change  
→ PR  
→ required CI  
→ merge  
→ fresh-read live main.

No direct-main mutation, protection bypass, or silent weakening is permitted.
